## The rule that decides every verdict

Bots never send a packet, and nothing under `soloMapling/` dispatches into a packet handler (`grep -rn "handlePacket\|AbstractPacketHandler" src/main/java/soloMapling` returns nothing). So:

- **Unreachable for a bot:** any path whose only entry is a packet handler, or an NPC/quest script the client starts. This is what retires the NPC shop, quest-meso and pet-loot paths.
- **Reachable for a bot:** methods bot code calls directly, *and* any code that takes a bot `Character` as the **counterparty** of a player action. The one leak found lives here.
- The ledger is the record (ticket 01): `BotHoldings.settle` hands a bot's deltas back to the world when it is not persisted; `discard` forgets them once durable. A credit that never reaches the ledger is value the bot's despawn destroys instead of returning - and, read the other way, a debit that never reaches it would mint value on settle.

## Findings that need a decision

These are recorded, not fixed: each is either ambient attraction behaviour or needs a policy the ADR has not set.

1. **The casino pays winners by conjuring chips.** `BlackjackDealerBot.java:560` `payWinner` loops a winner's bets and calls `DropCommands.botThrowItemToOwner` (`DropCommands.java:143`) per unit, which builds a *new* item via `BotLogic.generateCleanItem` (`BotLogic.java:142`) and places it on the floor. `BET_STAMPS` (`BlackjackDealerBot.java:45`) includes the meso-denominated chips `4002000-4002003`, and chip↔meso is lossless through the shop override (`CasinoChipConfig.getChipPrice`). Measured with a read-only WZ price probe: `4002000` = 10 000, `4002001` = 50 000, `4002002` = 250 000, `4002003` = 1 000 000 mesos (each equal to WZ `info/price` and to `CasinoChipConfig`). A winning hand pays `bet units x that item's face value` (`BlackjackDealerBot.java:563-573`), so the size of the mint is exactly the size of the bet. **Correction (grilling session, 2026-10-17):** a *bot* seat never bets a chip - its bet is a conjured `5 x 4031560` (Dark Lord stamp; `AI_BET_ITEM = 4031560`, `AI_BET_QTY = 5` at `BlackjackDealerBot.java:48-49`, emitted by `DropCommands.botDropItemQtyOwnerOnly` at `:645-646` with no meso and no inventory gate), and `4031560` appears nowhere else in the repo, so its WZ `info/price` is unverifiable here. The million-meso figure belongs to a *player* seat: a player may drop any `BET_STAMPS` chip (`:45`), `4002003` = 1 000 000 (`CasinoChipConfig.java:31`) with a par sell override (`Shop.java:208-210`), and a win then conjures one fresh copy *per unit* for the winner while the winner's own drop stays on the floor owned by them (`DropCommands.java:145-147`) - a player therefore doubles real-value chips per winning hand (x1.5 count on blackjack, `(int)(quantity * 1.5)` at `:565`) and cashes out at par, while each losing pot is looted into the dealer bot's ledger (`:603` -> `BotHoldings.creditDrop`) with no counter-entry anywhere, i.e. the dealer is a sink that also mints. Two riders: bots are seated every boot (`EnvironmentManager.java:159` boot wave 6, `:884-917`, 5 tables x 2-5 AI players), and `ITEM_LIMIT_ON_MAP = 200` (`config.yaml:328`) evicts the oldest drop on the map (`MapleMap.java:2225-2243`), so a placed bet can be deleted mid-hand. Fixing it means paying from a funded pot (a house bank), which is a design decision, not a leak repair.
2. **Conjured display items can land in durable bot holdings.** `DropCommands` conjures via `BotLogic.generateCleanItem*` for window/floor display; wherever a bot then loots one, `pickUpAndCredit` credits it like real value: the blackjack dealer's pot and card sweep (`BlackjackDealerBot.java:585,604,627`), the AI winner's own payout (`:585`), the OPQ hand-over copies (`OPQBot.java:511,733`). Every such item is 1-meso junk (`4001063`, `4001056-4001062`, `4031560` all priced 1, quest-flagged) and the amounts are trivial, but the mechanism contradicts ticket 01's precedent that a bot's generated offer is window-only value that "cannot be minted". Cheap containment if wanted: mark conjured drops at creation and have bot loot remove-without-credit.
3. **OPQ hand-over duplicates the pieces.** The bot loots the real reactor drop (`OPQBot.java:486`, `:705`) and then conjures a copy of each piece at the NPC for the hand-in (`:510-511` `botThrowItemQty`, `:732-733` `botThrowItem`). The bot keeps the real one and the world gets a fabricated one; the duplicates are 1-meso junk and purely cosmetic (the hand-in itself is the real player leader talking to `CHAMBERLAIN_EAK`, `OPQOrchestrator.java:351-371`), but the item count inflates by every run. Same containment as finding 2.
4. **A bot-owned `HiredMerchant`'s income is sunk.** `HiredMerchant.java:330-342` banks sale proceeds into the `merchanstore` row; only `withdrawMesos` (`:237` → `Character.withdrawMerchantMesos`) pays an owner, and its callers are player-only (`PlayerInteractionHandler.java:702,737`, `FredrickProcessor.java:290`). A bot never withdraws, so its merchant income is destroyed while its stock was generated. The ADR leaves "whether ambient merchants and scripted attractions are in scope for migration" undecided - this is that question, with one concrete instance.
5. **Latent robustness, not a leak:** `EventInstanceManager.unregisterPlayer` (`:389-406`) calls `dropExclusiveItems` (`:940-946`) outside its try, and `giveEventReward`/`giveEventPlayersMeso` (`:1026-1070`, `:202-235`) start from `Client.getPlayer()`. No OPQ script calls any of them (the leader's grants go through `cm.gainItem` in `scripts/npc/2013001.js:95-198`, which needs a real client), so nothing reaches a bot today. Recorded because a future event that registers bots would NPE there rather than fail cleanly.

## Policy decisions recorded (grilling session, 2026-10-17)

The owner reviewed findings 1-5 in a grilling pass. Findings 1-3 (the casino and conjure provenance) are **deferred** - not important now - but the policy for when that work resumes is settled, so the three answers are recorded here rather than re-litigated:

- **Pay from the pot; never conjure a payout** (finding 1). The collected bets are a real pot: hand those to the winner instead of fabricating copies with `BotLogic.generateCleanItem*`. Note this is player-facing, not bot-facing: a winning player currently keeps their own stake (it stays on the floor owned by them, `DropCommands.java:145-147`) *and* receives a conjured copy per unit, i.e. doubles real-value chips per winning hand and cashes them out at par through the lossless chip sell (`Shop.java:208-210`).
- **The 1.5x blackjack bonus is house-funded** (`BlackjackDealerBot.java:565`). The extra 0.5x units come out of the dealer bot's own looted holdings, same item id, taken through a new ledgered item-debit beside `noteMesoSpent` (`BotHoldings` has `creditDrop`/`grantItem`/`spendMeso` but no item-spend API today). The house pays what it holds and mints nothing; losing pots replenish it; the winner's own 1.0x is always safe.
- **A bot's bet stays a prop (never creditable)** (finding 2, and finding 3 by the same rule). Keep the conjured `5 x 4031560` display bet, but make conjured drops non-creditable and non-lootable by bots, so bot seats are value-free and every bot hand is cosmetic.
- **Provenance must be per-instance, not an id list.** The OPQ pieces are *both* real reactor drops (`OPQBot.java:486`, `:705`) and conjured copies of the same ids (`:510-511`, `:732-733`), so an id allowlist would wrongly block the legitimate pickup. The mark has to be set where the drop is created (the conjure helpers in `DropCommands`/`BotLogic.generateCleanItem*`); bot loot of a flagged drop removes it without crediting. Player looting is untouched.

Finding 4 facts, verified against the live database (container `solomapling-verify-db`, schema `cosmic_ticket06boot2`) rather than inferred: `characters` holds 2 rows and **0** of them join to `botstore` (0 by `id = 20000 + BotId`, 0 by name), and **0** rows have `MerchantMesos > 0`. A bot-owned merchant's proceeds are therefore **discarded, not banked**: `HiredMerchant.botBuy` sends a bot owner *deliberately* into the DB branch (`owner != null && !isBot(owner)`, `:866`), and `addMerchantMesos` (`client/Character.java:8929`) writes `characters.MerchantMesos` for a row that does not exist - 0 rows affected, no error, no log - while the in-memory `merchantmeso` it also sets is never persisted by `BotStore` (`UPDATE_ROW` carries no merchant column). The only path that moves this value into a wallet is `withdrawMerchantMesos()` (`client/Character.java:8957`), reachable only from player-side handlers.
